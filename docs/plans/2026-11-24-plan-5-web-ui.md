**Goal:** One page, served by the existing FastAPI app, that follows the demo flow in FR-8.1: paste a URL, prove control, see the score and the evidence, review fixes as diffs, approve, then explicitly download or copy the approved file.

**Architecture:** Static files (`index.html`, `app.css`, a few small ES modules) in `backend/app/ui/`, served by four explicit routes with strict security headers. No Node build step, no framework, no new Python dependency. The page talks only to the existing REST endpoints on its own origin. Every piece of site-derived text is placed in the page with `textContent` through a tiny element builder; the code base never uses `innerHTML`.

**Tech Stack:** HTML, CSS (custom properties, light and dark), vanilla ES modules (Node 20+ only for the tests: `node --test` with a small hand-written fake DOM, no npm packages), FastAPI/Starlette (existing).

**Spec:** AgentReady PRD (https://claude.ai/artifact/2CLFRC7VzK9iRbN5daPmUd) FR-8.1 ("One flow: paste a URL, prove control, see the score and evidence, review fixes as a diff, approve. The demo video follows exactly this flow."), FR-6.2 (diff shown), FR-6.3 (approve first, then explicitly download or copy; approval exports nothing; the app never deploys), FR-4 (evidence for every finding, "not detected" wording), and the Safety table.

## Global Constraints
- The UI is a client of the existing REST API only. **No new backend capability**: no endpoint that audits, fetches, approves or exports differently from the REST API; the only Python changes are four read-only routes that serve the static files, plus the call that registers them.
- **Escaping:** no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`, string-argument timers, `srcdoc` or `javascript:` anywhere in `backend/app/ui/` (a test scans for them). Site text is only ever set with `textContent` / text nodes. Attributes are set only from an allowlist (`class`, `id`, `type`, `disabled`, `hidden`, `role`, `aria-*`, `data-*`, `for`, `open`, `value`, `placeholder`, `autocomplete`, `spellcheck`, `rel`, `href`, `download`, `title`), `on*` attributes are never set, and `href` is accepted only for fixed in-app destinations through `safeHref`. **Site-derived URLs (finding URLs, diffs, fix paths) are shown as text and never become links**, because a blocked redirect target can appear in a finding's `url`.
- **Headers:** `GET /` and `GET /ui/<file>` send `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. The page has no inline script, no inline style and no inline event handler. These headers apply to the UI routes only; no REST response changes (the REST parity tests from Plan 4 must still pass).
- **Credential handling:** the report id is the only credential for approval and export. Keep it in a JS variable and in `sessionStorage` (inside `try/catch`; the page must work when storage throws); **never** put it in the URL, hash, history or page text, and never log it.
- **Wording (PRD):** statuses are shown exactly as `detected`, `not detected`, `unreachable`. Never write "absent", "missing", "no CAPTCHA", "secure" or "passed" as a claim about the site. Unreachable findings are labelled "could not be checked, not in the score". The approval step states: "Approving does not change your site. After approving, download or copy the file and add it to your site yourself."
- **Accessibility:** every control has a visible label, one `h1`, logical heading order, a skip target, a polite live region for status messages, full keyboard operation, visible focus rings, meaning never carried by colour alone, `prefers-color-scheme` dark tokens, `prefers-reduced-motion` respected, layout works at 360 px wide with a 16 px gutter and no horizontal page scroll.
- The test count in each task is a floor, not a target: report the real number.

## Design (ui-design skill; references and rules)
- **References:** Lighthouse's report (one 0 to 100 score with bands, per-category scores, failing audits first, each audit expandable to its evidence; see https://developer.chrome.com/docs/lighthouse/overview) and GitHub's pull-request review (unified diff, one high-contrast approve action). The GitHub reference is from the author's knowledge, not from a fetched page.
- **Layout:** one centred column (max 760 px), four numbered steps on one page, each step a card; a step is expanded when it is the current one and summarised when done.
- **Tokens:** spacing scale 4, 8, 16, 24, 32, 48 only. Colour: neutral base + one accent (used only for the primary action, focus ring and the score bar fill). Type: one system font stack, body 16 and small 14 only, headings 24, 20, 18. Destructive-looking actions (Reject, Revoke) are secondary outlined buttons, not red blocks. Dark mode through the same tokens.
- **Score:** large number + text band + proportional bar. Bands (text, not colour): 90 to 100 "Good", 50 to 89 "Needs work", 0 to 49 "Poor"; `score_status: "not_scored"` shows "Not scored" with the reason sentence. Show `unscored` as "N checks could not be reached and are not in the score".
- **Findings:** grouped by category, "Needs attention" (not passed) before "OK so far" (passed), each a `<details>` row: summary = check name + status chip + confidence chip; body = what was checked, what was observed, the URL as text.
- **Fixes:** card per fix: kind title, plain description, status chip, optional warning, diff viewer (monospace, `+` lines tinted and prefixed, `-` lines tinted and prefixed, so colour is not the only cue; `excerpt` diffs are labelled "Excerpt: the full page is not shown"), actions. One primary button per card: "Approve" when proposed; after approval "Download" (primary) and "Copy" (secondary) and "Revoke approval" (secondary). Rejected: a quiet "Rejected" chip, no actions. Skipped kinds are listed in a "Not proposed" disclosure with their reasons.
- **One primary action per step:** Step 1 "Verify and audit"; Step 3 "Propose fixes"; Step 4 per fix as above. Re-audit after deploying is a secondary button ("Re-audit with fresh pages") that sends a new snapshot name `rerun-<UTC yyyymmddhhmmss>`.

## Decisions made here (flag to the owner)
1. **Vanilla ES modules served by FastAPI**, not React/Vite (the earlier plan mentioned Vite): no build step and no `node_modules` makes the clean-checkout run and the demo simpler. Node is needed only to run the UI unit tests; if Node is absent the pytest wrapper skips them with a clear message.
2. **Four explicit routes** (`/`, `/ui/<file>` with a fixed allowlist computed at import) instead of `StaticFiles`: no directory traversal surface, and exact headers.
3. The page is served at `/` on the same origin as the API, so no CORS is needed and none is added.
4. Files are read into memory at import, so editing them needs a restart (stated in `docs/ui.md`).

- `HEAD` and other methods keep the framework default (405 with `Allow`).

### Task 3: API client and state

**Files:** Create `ui/api.js`, `ui/state.js`, `tests/ui/api.test.mjs`, `tests/ui/state.test.mjs`.

**Interfaces:**
- `api.js` exports `createApi(fetchImpl, { timeoutMs = 60000 } = {})`. Every method returns `{ ok: true, data }` or `{ ok: false, kind, status, message, instructions? }`; it never throws. Kinds: `unverified` (HTTP 403; `instructions` is the response's `detail` object: `token`, `meta_tag`, `meta_tag_placement`, `dns_txt_name`, `dns_txt_value`, `dns_note`, `domain`), `invalid` (422; `message` is the `detail` string if it is a string, else "The request was not valid."), `not_found` (404), `conflict` (409; `message` from `detail`), `busy` (429/503), `network` (fetch rejected or timeout via `AbortController`), `server` (anything else). Never include raw response text or exception text in `message`; use fixed sentences.
  - Methods: `ownershipToken(domain)` → `GET /ownership-token?domain=<encoded>`; `audit(url, snapshot = "default")` → `POST /audit` JSON `{url, snapshot}`; `report(id)`; `proposeFixes(id)` → `POST /report/{id}/fixes`; `listFixes(id)` → `GET`; `approve(id, fixId)`, `reject(id, fixId)` → `POST .../approve|reject`; `exportFix(id, fixId)` → `GET .../export`. Ids are validated before use: `id` must match `^[0-9a-f]{32}$`, `fixId` must match `^[a-z_]{1,32}$`, else return `{ok:false, kind:"invalid"}` without calling fetch. URL path segments are `encodeURIComponent`-encoded anyway.
- `state.js` exports `createStore(storage)` where `storage` may be `null` or throw: `{ get(), set(patch), subscribe(fn), saveReportId(id), loadReportId(), clearReportId() }`. The report id is stored under one `sessionStorage` key inside `try/catch` (failures are ignored); `get()` never contains the id in any string that is rendered by Task 4 (the id is accessed only through `getReportId()`); steps: `enter`, `verify`, `auditing`, `report`, `fixes`.
